# Boring Vectors — Post-v1 Roadmap

_Last consolidated 2026-10-03. Covers the three features decided on after the v1 parity pass and new-project scope (`docs/SPEC.md` steps 1–7, all done — see `CLAUDE.md` Status): multiple projects, animation, and export. This file is a reference for the current state of that work and the decisions behind it — not a chronological changelog; `git log` is authoritative for history._

## Status: all three areas done

- **Projects** — multiple named, autosaved, switchable projects (rename of the original "documents" concept).
- **Export** — SVG (clipboard/download), raster PNG/JPG, portable project-file export/import.
- **Animation** — a keyframe timeline: opacity, position (X/Y), size (width/height), rotation, ratio-based scale, fill color, stroke color, and per-keyframe easing. Feature-flagged off by default (Settings → "Animation timeline (beta)") since it's still young; a "Loop timeline playback" setting is available alongside it.
- **Animated export** — every animatable property bakes into a standalone-playable SVG (SMIL `<animate>`), plus GIF and WebM video export.

## Architecture decisions (read before touching this code)

**Animation clip is a second source of truth, deliberately.** CLAUDE.md's key architectural rule says Paper.js's `Project` is the sole source of truth for path geometry — not duplicated into the store. Animation keyframe data doesn't fit that: it isn't live geometry, it's timeline data describing geometry *over time*, which Paper.js has no concept of. The amendment, now in CLAUDE.md: Paper.js remains authoritative for a path's *current, static* geometry when not animating; the store's `animation` slice (clips keyed by path id + property) is authoritative for *how that geometry changes over time*. Playback writes interpolated values onto live Paper.js objects each frame; it never reads them back as truth. This is why `src/animation.ts` exists as a standalone, Paper.js-free module (pure data + pure functions), and why `PaperCanvas.tsx`/`canvasEngine/animationPlayback.ts` are the only places that turn that data into live geometry.

**Path identity is `path.name`, not Paper.js's `.id`.** Paper's `.id` is a per-session auto-incrementing counter — it gets reassigned on every reload/re-import, so anything persisted by path id (keyframes included) would silently orphan itself on the next reload. Every path gets a UUID `.name` assigned at creation time (import, pen tool, shape tool — see `hitTest.ts`'s `ensurePathName`), which Paper.js round-trips through the SVG `id` attribute on export/import, so it survives reload. All path identity — selection, hit-testing, animation — is keyed by `.name`.

**Rotation and ratio-scale need a "rest geometry" snapshot; nothing else does.** Opacity, X/Y, width/height, and color are all stored and applied as *absolute* values, so evaluating a keyframe never depends on transient state. Rotation/scale can't work that way: Paper.js bakes transforms directly into a path's segment data rather than keeping a separate matrix, so "rotate to 45°" only means something relative to a fixed rest shape. `PathTrack.restSegments`/`restCenter` (in `animation.ts`) capture that rest shape once, the first time rotation or scale is keyframed for a path — captured from live Paper.js state via a mediated store request (`transformKeyframeRequest`), since only `PaperCanvas.tsx` can read that state. Playback resets to a fresh clone of the rest snapshot every frame, then reapplies scale/rotation around `restCenter` — never incrementally. **Known limitation**: the rest snapshot isn't pruned when a path's rotation/scale keyframes are all deleted (only when the whole path track is removed) — node-editing such a path afterward can get silently overwritten on the next playhead change. Accepted for now; narrow edit-after-animate workflow.

**Color is three synced numeric channels, not a dedicated type.** `fillColorR`/`G`/`B` and `strokeColorR`/`G`/`B` (0–255) reuse the same absolute-numeric keyframe machinery as everything else instead of a parallel color-keyframe shape. They're always keyed/moved/removed together from `Timeline.tsx`, so a path has all three of a trio or none.

**SMIL export takes two different strategies depending on the property.** Opacity and color map 1:1 onto a native `<animate attributeName="...">`, with the SVG renderer doing the actual interpolation — `buildSmilAnimate()`/`buildSmilColorAnimate()` in `animation.ts` just emit the keyframe list; nothing there performs interpolation. Position/size/rotation/scale don't have that direct a mapping (same reasons as the rest-geometry note above), so instead the exporter densely samples the path's geometry at 24fps across the animation's duration on an offscreen clone (reusing `applyGeometryAtTime`, the exact function live playback uses) and bakes the result into one `<animate attributeName="d" calcMode="linear">`. Easing is effectively "pre-baked" by the sampling itself.

**GIF/video reuse one frame-rendering pipeline**, itself built on the same `applyFullAnimationAtTime` playback function: `renderAnimationFrames(fps, scale)` in `canvasEngine/svgExport.ts` pre-renders the whole animation into an array of offscreen canvases. GIF encodes them via `gif.js` (a new dependency — browsers have no native GIF encoder) using a Web Worker. Video uses the browser's native `MediaRecorder` on a `canvas.captureStream()` — no new dependency — drawing each pre-rendered frame at a steady interval in real time, so recording takes about as long as the animation's own duration.

## Code layout

Animation/export logic is split the same way `tools.ts`/`hitTest.ts`/`overlay.ts` already split tool/hit-test/overlay logic out of `PaperCanvas.tsx` — factories that take `contentLayer`/`storeRef` once, wired together in `PaperCanvas.tsx`'s mount effect:

- `src/animation.ts` — pure data model and functions (no Paper.js, no React): `AnimationClip`/`PathTrack`/`Keyframe` types, `evaluateProperty` (interpolation), `withKeyframeSet`/`Removed`/`Moved` (immutable updates for Zustand), SMIL-building helpers.
- `src/canvasEngine/animationPlayback.ts` — `applyGeometryAtTime`/`applyFullAnimationAtTime`/`applyAnimationAtTime` (write keyframe values onto live or cloned Paper.js paths) and `createPlaybackController` (the rAF playback loop, including loop-vs-pause-at-end).
- `src/canvasEngine/svgExport.ts` — `createSvgExporter`: static SVG, animated SVG (SMIL), raster (PNG/JPG), GIF, video.
- `src/components/Timeline.tsx` — the UI: one stacked track row per animatable property, driven by a `PROPERTY_DEFS`/`COLOR_ROW_DEFS` table (adding a new *absolute-valued* property is a table entry + a write branch in `animationPlayback.ts`, not a UI rewrite), docked as an overlay inside `CanvasWrap.tsx` rather than a flex layout sibling (so opening it never resizes the canvas — see the Rulers-desync bug this fixed). Its header controls (play/duration/easing/Done) are `position: sticky` inside the scrollable body, so they stay visible while the property rows below scroll — the resize handle (`.Timeline-resizeHandle`) needs a higher z-index than the sticky header to stay grabbable where the two overlap (see the regression note below).
- `src/canvasEngine/tools.ts` — also owns the Select tool's resize/rotate handles (`computeResizedBounds`, exported for unit testing) alongside drag/marquee selection.

## Testing

`npm test` runs Vitest unit tests (`src/**/*.test.ts`: `animation.ts`'s pure logic — interpolation, immutable keyframe updates, auto-key, SMIL generation — plus `canvasEngine/tools.ts`'s `computeResizedBounds`, paper.js geometry classes work fine in Vitest's node environment without a `paper.setup()` scope). `npm run test:e2e` runs the checked-in Playwright suite (`e2e/`) against a dev server it starts itself — tools, projects, export, and animation/playback/auto-key/transform-handles/easing-editing, all against a real browser. `e2e/helpers.ts` has the shared setup (`importSampleShape`, `enableAnimateMode`, `timelineTrackBox`, `readPositionProps`, `pathPointToScreen`, `shrinkTimeline`/`growTimeline`). See "Known gaps" below for what isn't covered yet.

**Converting a canvas-space point to a screen point for a mouse-driven e2e gesture**: `pathPointToScreen()` mirrors `background.ts`'s `fitCanvasInView` math (`scale = min((viewW-80)/canvasW, (viewH-80)/canvasH)`, centered) — reliable as long as the test hasn't panned/zoomed/resized the canvas off that initial fit. Guessing screen offsets by eyeballing a screenshot works for one-off manual verification but is fragile for a committed test; prefer reading the shape's actual bounds from the Properties panel (`readPositionProps`) and computing the exact handle position from them.

**The Timeline panel overlays most of the canvas at its default height** (560px — see Code layout above), which blocks mouse-driven direct manipulation of a shape near canvas center in Animate mode. `shrinkTimeline()`/`growTimeline()` drag its resize handle to work around this; a test that skips this step but drags on the canvas in Animate mode may silently hit the Timeline panel instead of the shape and assert on a no-op (this happened once — see the "Fixed" section below).

## Known gaps / not done

- Rest-geometry pruning isn't implemented: the rest snapshot (`PathTrack.restSegments`/`restCenter`) isn't cleared when a path's rotation/scale keyframes are all deleted (only when the whole path track is removed) — node-editing such a path afterward can get silently overwritten on the next playhead change. Accepted for now; narrow edit-after-animate workflow.
- GIF/video export always renders exactly one pass regardless of the "Loop timeline playback" setting — a looping GIF is a separate, unrequested feature.
- Automated tests cover `animation.ts`'s and `tools.ts`'s pure logic (43 Vitest unit tests) and core workflows end-to-end (23 Playwright specs in `e2e/`: tools, projects, export, animation/playback/auto-key/transform-handles/easing). Not yet covered: `editorStore.ts`'s other slices, `canvasEngine/hitTest.ts`/`overlay.ts`/`svgIO.ts` in isolation, GIF/video export (only exercised manually so far — real-time recording and Web Worker encoding don't fit neatly into a fast e2e run), and PNG/SVG-content-correctness assertions beyond "a file downloaded and isn't empty".

## Fixed: Timeline fields/overlay went stale while scrubbing

Two compounding bugs, both found from a user report ("moving to a timeframe doesn't show updates to transformed objects") and confirmed by reproduction before fixing:

1. The playhead-change handler in `PaperCanvas.tsx` called `applyAnimationAtTime` (which correctly moves/rotates/recolors the live path) but never refreshed the selection overlay or `selectedPathProps` — the data Timeline's property rows and the Properties panel read from. The canvas was right; the panels were stale, only updating on selection changes. Fixed by splitting `redrawOverlay` into `refreshSelectionDisplay` (overlay redraw + `selectedPathProps` refresh, no side effects) and the autosave-scheduling wrapper around it, and calling the former on every playhead change too — without triggering autosave on every animation frame during playback.
2. Separately, `Timeline.tsx`'s per-property `valueOverrides`/`colorOverrides` (used to preview a value before clicking "Key") never got cleared after the keyframe was actually set, so a field stayed pinned to whatever was last typed regardless of scrubbing, masking even the corrected live value from fix (1). Fixed by clearing the relevant override once its keyframe is committed.

Verified precisely: keyed X at 355 (t=0) and 555 (t≈end), confirmed the field showed ~455 at the midpoint scrub and progressed smoothly (405→573) across five samples during actual playback — not just manual scrub clicks.

## Direct manipulation extends animations already in progress

Resolves the "no auto-keying" gap: dragging a shape (or editing its position/fill/stroke via the Properties panel) while in Animate mode now keeps the keyframe system in sync. The design call made here (not explicitly specified, picked as the safest default): **direct manipulation extends an animation already in progress — it never starts a new one.**

- If the property already has a keyframe at exactly the current playhead time, its value is updated (time/easing unchanged).
- If the property is already animated (has a track from being keyed at least once for this path) but has no keyframe at this exact time, a new one is inserted there, inheriting easing from whichever existing keyframe is nearest in time — so posing a new frame doesn't reset the curve to linear.
- If the property has never been keyframed for this path at all, direct manipulation is left exactly as it was: a plain, unrecorded edit, same as Draw mode. Dragging a shape you've never animated doesn't suddenly start animating it.

`withKeyframeAutoInserted()` (`animation.ts`) implements this; `syncKeyframesAfterDirectEdit()` (`canvasEngine/animationPlayback.ts`) is the shared hook — called from the Select tool's drag-commit and resize/rotate-handle commit (`tools.ts`) and from `PaperCanvas.tsx`'s `applyPropsEdit` (position/stroke/fill edits). It checks x/y, width/height, and both color trios directly from the live path's bounds/colors; rotation is different (see next section) and is passed in explicitly as a delta by the caller.

Verified all three cases: dragging at an already-keyed time updates that keyframe (1→1, value changes); dragging at a new time on an already-animated property inserts a new keyframe (1→2) whose value survives a scrub-away-and-back; dragging a property that's never been animated creates nothing (0→0), confirmed as a control alongside the other two in the same test run.

## Resize/rotate handles, easing editing, and a sticky-header regression

Three follow-up improvements to the animation-authoring experience, done together:

**1. Resize and rotate handles on the Select tool's selection overlay.** Previously width/height/rotation/scale could only be set by typing into the Timeline's own fields — there was no on-canvas handle, which was the reason `syncKeyframesAfterDirectEdit` didn't cover those properties (see the old "Known gaps" entry this resolves). `overlay.ts`'s `drawTransformHandles()` draws 8 resize handles (corners + edge midpoints) and one rotate handle (offset above top-center, screen-space-constant size regardless of zoom) whenever the Select tool has a single path selected; `tools.ts`'s `createSelectTool` checks these via `hitTestOverlay` before falling through to its normal path-hit/marquee logic.

- Resize drags the dragged corner/edge while the opposite corner/edge stays anchored (`computeResizedBounds`, pure and unit-tested), by directly reassigning `path.bounds` — the same mechanism `applyGeometryAtTime` already uses for width/height keyframes, so it composes with existing behavior for free. Shift preserves aspect ratio on a corner drag. Resize syncs through the generic x/y/width/height path in `syncKeyframesAfterDirectEdit` — no new sync code needed.
- Rotate calls `path.rotate()` directly on the live path (shift snaps to 15° increments) and tracks the gesture's net rotation in degrees. Because rotation keyframes store an absolute angle relative to captured rest geometry (not something live Paper.js state can be read back as — see the rest-geometry architecture note above), the handle can't reuse the generic bounds-reading sync path: it passes the gesture's rotation *delta* to `syncKeyframesAfterDirectEdit`, which — only if a rotation track already exists for the path (auto-key never starts a new animation, same rule as everything else) — adds that delta to whatever the rotation track currently evaluates to at the playhead and auto-keys the result.
- Deliberately *not* synced: resizing never touches `scale` keyframes. `scale` is a rest-geometry-relative multiplier (a parallel, older mechanism for proportional animation); resize's width/height-based bounds mutation is a different, newer mechanism, and `applyGeometryAtTime` already lets width/height tracks override scale/rotation's rest-based sizing when both exist. Driving `scale` from a resize-handle delta would make two mechanisms fight over the same pixels.

**2. Click a keyframe diamond to edit its easing**, instead of delete-and-re-add being the only way to change it. A plain click (no horizontal movement past a small threshold) opens an inline editor in the Timeline header with an easing `<select>` (writes through the existing `setKeyframe` with the keyframe's own time/value, easing only) and a Delete button; works for both plain-property and color-trio (all three channels share one editor) rows.

   Implementing this exposed a real interaction conflict: a `dblclick` (the existing delete gesture) is two independent `mousedown`→`mouseup` pairs, and the first pair alone looks exactly like a single click — opening the easing editor **immediately** on every click meant the editor popped in between a dblclick's two clicks, which (since the editor is in-flow, not floating) shifted the Timeline's layout and made the dblclick's second click land somewhere else, silently breaking delete. Fixed by delaying the editor open by `DBLCLICK_WINDOW_MS` (300ms) and having the dblclick handler cancel the pending timer first — standard click/dblclick disambiguation, applied here because the popover affects layout instead of being a floating overlay.

**3. Timeline header controls (`.Timeline-controls`) are now `position: sticky`** inside the scrollable panel body, so play/duration/easing/Done stay visible while property rows scroll underneath — a user-requested tweak, done alongside the above.

**Regression caught by the new e2e tests before merge, not after**: making the header sticky (`z-index: 2`) silently broke the Timeline's own resize handle (`.Timeline-resizeHandle`, `z-index: 1`, positioned to straddle the panel's top edge) — the sticky header now painted over it, so dragging the handle hit the header instead and did nothing. Caught because a new e2e test needed to shrink the Timeline (to stop it from overlapping the canvas — see the Testing section above) and the shrink silently no-opped. Fixed by raising the handle's z-index above the header's. This is also why the pre-existing "direct manipulation updates an existing keyframe" test got reworked: it turned out to have the same latent gap — its drag coordinates also landed on the Timeline panel instead of the canvas, and the test never asserted the value actually *changed*, only that it stayed consistent across a scrub — so it was silently passing without exercising the drag at all. Both are fixed now (the fixed test asserts `afterDrag !== beforeDrag`).
