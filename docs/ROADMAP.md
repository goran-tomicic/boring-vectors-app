# Boring Vectors — Post-v1 Roadmap

_Last consolidated 2026-10-03. Covers the three features decided on after the v1 parity pass and new-project scope (`docs/SPEC.md` steps 1–7, all done — see `CLAUDE.md` Status): multiple projects, animation, and export. This file is a reference for the current state of that work and the decisions behind it — not a chronological changelog; `git log` is authoritative for history._

## Status: all three areas done

- **Projects** — multiple named, autosaved, switchable projects (rename of the original "documents" concept).
- **Export** — SVG (clipboard/download), raster PNG/JPG, portable project-file export/import.
- **Animation** — a keyframe timeline: opacity, position (X/Y), size (width/height), rotation, ratio-based scale, fill color, stroke color, and per-keyframe easing. Feature-flagged off by default (Settings → "Animation timeline (beta)") since it's still young; a "Loop timeline playback" setting is available alongside it.
- **Animated export** — every animatable property bakes into a standalone-playable SVG (SMIL `<animate>`), plus GIF and WebM video export.

## Architecture decisions (read before touching this code)

**Animation clip is a second source of truth, deliberately.** CLAUDE.md's key architectural rule says Paper.js's `Project` is the sole source of truth for path geometry — not duplicated into the store. Animation keyframe data doesn't fit that: it isn't live geometry, it's timeline data describing geometry *over time*, which Paper.js has no concept of. The amendment, now in CLAUDE.md: Paper.js remains authoritative for a path's *current, static* geometry when not animating; the store's `animation` slice (clips keyed by path id + property) is authoritative for *how that geometry changes over time*. Playback writes interpolated values onto live Paper.js objects each frame; it never reads them back as truth. This is why `src/animation.ts` exists as a standalone, Paper.js-free module (pure data + pure functions), and why `PaperCanvas.tsx`/`canvasEngine/animationPlayback.ts` are the only places that turn that data into live geometry.

**Path identity is `path.name`, not Paper.js's `.id`.** Paper's `.id` is a per-session auto-incrementing counter — it gets reassigned on every reload/re-import, so anything persisted by path id (keyframes included) would silently orphan itself on the next reload. Every path gets a UUID `.name` assigned at creation time (import, pen tool, shape tool — see `hitTest.ts`'s `ensurePathName`), which Paper.js round-trips through the SVG `id` attribute on export/import, so it survives reload. All path identity — selection, hit-testing, animation — is keyed by `.name`.

**Rotation and ratio-scale need a "rest geometry" snapshot; nothing else does.** Opacity, X/Y, width/height, and color are all stored and applied as *absolute* values, so evaluating a keyframe never depends on transient state. Rotation/scale can't work that way: Paper.js bakes transforms directly into a path's segment data rather than keeping a separate matrix, so "rotate to 45°" only means something relative to a fixed rest shape. `PathTrack.restSegments`/`restCenter` (in `animation.ts`) capture that rest shape once, the first time rotation or scale is keyframed for a path — captured from live Paper.js state via a mediated store request (`transformKeyframeRequest`), since only `PaperCanvas.tsx` can read that state. Playback resets to a fresh clone of the rest snapshot every frame, then reapplies scale/rotation around `restCenter` — never incrementally. **Known limitation**: the rest snapshot isn't pruned when a path's rotation/scale keyframes are all deleted (only when the whole path track is removed) — node-editing such a path afterward can get silently overwritten on the next playhead change. Accepted for now; narrow edit-after-animate workflow.

**Color is three synced numeric channels, not a dedicated type.** `fillColorR`/`G`/`B` and `strokeColorR`/`G`/`B` (0–255) reuse the same absolute-numeric keyframe machinery as everything else instead of a parallel color-keyframe shape. They're always keyed/moved/removed together from `Timeline.tsx`, so a path has all three of a trio or none.

**SMIL export takes two different strategies depending on the property.** Opacity and color map 1:1 onto a native `<animate attributeName="...">`, with the SVG renderer doing the actual interpolation — `buildSmilAnimate()`/`buildSmilColorAnimate()` in `animation.ts` just emit the keyframe list; nothing there performs interpolation. Position/size/rotation/scale don't have that direct a mapping (same reasons as the rest-geometry note above), so instead the exporter densely samples the path's geometry at 24fps across the animation's duration on an offscreen clone (reusing `applyGeometryAtTime`, the exact function live playback uses) and bakes the result into one `<animate attributeName="d" calcMode="linear">`. Easing is effectively "pre-baked" by the sampling itself.

**GIF/video reuse one frame-rendering pipeline**, itself built on the same `applyFullAnimationAtTime` playback function: `renderAnimationFrames(fps, scale)` in `canvasEngine/svgExport.ts` pre-renders the whole animation into an array of offscreen canvases. GIF encodes them via `gif.js` (a new dependency — browsers have no native GIF encoder) using a Web Worker. Video uses the browser's native `MediaRecorder` on a `canvas.captureStream()` — no new dependency — drawing each pre-rendered frame at a steady interval in real time, so recording takes about as long as the animation's own duration.

## Code layout

Animation/export logic is split the same way `tools.ts`/`hitTest.ts`/`overlay.ts` already split tool/hit-test/overlay logic out of `PaperCanvas.tsx` — factories that take `contentLayer`/`storeRef` once, wired together in `PaperCanvas.tsx`'s mount effect:

- `src/animation.ts` — pure data model and functions (no Paper.js, no React): `AnimationClip`/`PathTrack`/`Keyframe` types, `evaluateProperty` (interpolation), `withKeyframeSet`/`Removed`/`Moved` (immutable updates for Zustand), SMIL-building helpers.
- `src/canvasEngine/animationPlayback.ts` — `applyGeometryAtTime`/`applyFullAnimationAtTime`/`applyAnimationAtTime` (write keyframe values onto live or cloned Paper.js paths) and `createPlaybackController` (the rAF playback loop, including loop-vs-pause-at-end).
- `src/canvasEngine/svgExport.ts` — `createSvgExporter`: static SVG, animated SVG (SMIL), raster (PNG/JPG), GIF, video.
- `src/components/Timeline.tsx` — the UI: one stacked track row per animatable property, driven by a `PROPERTY_DEFS`/`COLOR_ROW_DEFS` table (adding a new *absolute-valued* property is a table entry + a write branch in `animationPlayback.ts`, not a UI rewrite), docked as an overlay inside `CanvasWrap.tsx` rather than a flex layout sibling (so opening it never resizes the canvas — see the Rulers-desync bug this fixed). Its header controls (play/duration/easing/Done) are `position: sticky` inside the scrollable body, so they stay visible while the property rows below scroll — the resize handle (`.Timeline-resizeHandle`) needs a higher z-index than the sticky header to stay grabbable where the two overlap (see the regression note below).
- `src/canvasEngine/tools.ts` — also owns the Select tool's resize/rotate handles (`computeResizedBounds`, exported for unit testing), its node-anchor click-to-edit handoff into the Node tool, and the live on-canvas resize/rotate label, alongside drag/marquee selection.
- `src/canvasEngine/layers.ts` — pure, Paper.js-geometry-only (no React): `inferShapeKind`/`computeLayerList`, the Layers panel's name-inference logic (see "Layers panel" below).
- `src/components/LayersPanel.tsx` — the Layers panel UI; reads `editorStore`'s `layers` (written by `PaperCanvas.tsx` only) and `selectedPathIds` directly, so panel↔canvas selection sync needed no new wiring beyond what `selectedPathIds` already drove. `Timeline.tsx` reads the same `layers` list to group its property rows by shape (see "Timeline grouped by shape" below).
- `src/components/usePanelResize.ts` — shared drag-to-resize hook for `LayersPanel.tsx`/`PropsPanel.tsx`, throttled to one width update per animation frame (see "Fixed: side-panel resize could desync the ruler" below for why).

## Testing

`npm test` runs Vitest unit tests (`src/**/*.test.ts`: `animation.ts`'s pure logic — interpolation, immutable keyframe updates, auto-key, SMIL generation — plus `canvasEngine/tools.ts`'s `computeResizedBounds`, paper.js geometry classes work fine in Vitest's node environment without a `paper.setup()` scope). `npm run test:e2e` runs the checked-in Playwright suite (`e2e/`) against a dev server it starts itself — tools, projects, export, and animation/playback/auto-key/transform-handles/easing-editing, all against a real browser. `e2e/helpers.ts` has the shared setup (`importSampleShape`, `enableAnimateMode`, `timelineTrackBox`, `readPositionProps`, `pathPointToScreen`, `shrinkTimeline`/`growTimeline`). See "Known gaps" below for what isn't covered yet.

**Converting a canvas-space point to a screen point for a mouse-driven e2e gesture**: `pathPointToScreen()` mirrors `background.ts`'s `fitCanvasInView` math (`scale = min((viewW-80)/canvasW, (viewH-80)/canvasH)`, centered) — reliable as long as the test hasn't panned/zoomed/resized the canvas off that initial fit. Guessing screen offsets by eyeballing a screenshot works for one-off manual verification but is fragile for a committed test; prefer reading the shape's actual bounds from the Properties panel (`readPositionProps`) and computing the exact handle position from them.

**The Timeline panel overlays most of the canvas at its default height** (560px — see Code layout above), which blocks mouse-driven direct manipulation of a shape near canvas center in Animate mode. `shrinkTimeline()`/`growTimeline()` drag its resize handle to work around this; a test that skips this step but drags on the canvas in Animate mode may silently hit the Timeline panel instead of the shape and assert on a no-op (this happened once — see the "Fixed" section below).

## Layers panel, and shape names inferred from geometry

A Figma-style Layers panel: a left-hand list of every path in the current project, click-to-select in either direction (panel → canvas selection, and canvas/Properties-panel selection → highlighted row), toggleable via a new bottom-left pill (`LayersToggle`) mirroring the existing bottom-right `PanelToggle` for the Properties panel. Docked as a flex sibling in `App.tsx` (not an overlay) — unlike the Timeline, this is safe: `PropsPanel` already does the same thing on the right, and `PaperCanvas.tsx`'s `ResizeObserver` on the canvas element already re-fits the view correctly on any flex-layout change, so there's no Rulers-desync risk here (that bug was specific to the Timeline being naively added as a flex sibling instead of an overlay — see the "Timeline fields/overlay went stale" section below for the unrelated bug it's easy to confuse this with).

**Names are inferred from geometry by default, with an optional stored override per path.** A path carries no "I was created with the Rectangle tool" tag — once created, a rectangle-tool rectangle and a hand-drawn rectangle-shaped pen path are both just a generic `paper.Path`. `layers.ts`'s `inferShapeKind()` recomputes a label from the path's current geometry every time the layer list is rebuilt:

- **Line**: open path, exactly 2 segments, no bezier handles.
- **Rectangle**: closed, exactly 4 segments, no handles, *and* its area fills its own bounding box — that last check is what's needed to exclude a diamond (also a closed 4-segment straight-edged quad, just not axis-filling) from being misnamed "Rectangle". Caught by a unit test before it could ship: an early version of the heuristic didn't have the area check and classified a diamond test fixture as a rectangle.
- **Ellipse**: closed, exactly 4 segments, every segment has a handle, and its area matches an ellipse inscribed in its bounding box (same reasoning as the rectangle check, applied to curves).
- **Shape**: the fallback for everything else — pen-drawn paths, stars, imported SVGs, or a rectangle/ellipse that's since been reshaped by node-editing into something that no longer passes the geometric check. This means a layer's name can change as you edit it (a rectangle you drag a node on stops being called "Rectangle" once it's no longer rectangular) — intentional, not a bug: the name always reflects current geometry, not creation history.

**Numbering only kicks in once a kind repeats.** `computeLayerList()` counts paths by inferred kind first; a kind with exactly one path stays bare ("Rectangle"), and only a kind with two or more gets suffixed ("Rectangle 1", "Rectangle 2", …). The list itself is ordered frontmost-first — Paper.js layer children are stored back-to-front, so `computeLayerList()` reverses them to match how layer lists conventionally read (topmost in the list = topmost/frontmost on canvas), with numbering assigned in that same frontmost-first order.

**Refreshed on structural change, not every frame.** `PaperCanvas.tsx` calls a `refreshLayers()` helper (pushes `computeLayerList(contentLayer, storeRef.current.layerNameOverrides)` into the store's `layers` field) from the same places that already call `commitHistory()` — tool-finish, delete, import — plus `restoreSnapshot()` (undo/redo) and `loadProjectIntoCanvas()` (project load/switch) explicitly, since those don't go through `commitHistory()`, and the `layerNameOverrides` subscription watcher below. Deliberately *not* hooked into `redrawOverlay()`, which fires on every drag frame — a shape's inferred kind essentially never changes mid-drag (bounds-resize keeps segment count/handle-zero-ness; only node-editing can flip a kind, and only at gesture-end when `commitHistory()` fires anyway), so recomputing the whole list every frame would be pure waste.

**Selection sync needed no new plumbing.** The panel reads `selectedPathIds` directly from the store and calls the same `setSelection()` action canvas clicks already use — both directions were already fully store-driven before this feature existed, so "select in panel, see it selected on canvas" and the reverse both fell out for free once the panel existed at all.

The Timeline now does group by shape using this panel's own `layers` list — see "Timeline grouped by shape" below.

## Layer renaming, and horizontal panel resizing

Two follow-ups to the Layers panel above.

**Renaming is a stored override, layered on top of the inferred name.** `editorStore`'s `layerNameOverrides` (`Record<pathId, name>`) persists in `ProjectPayload.layerNames` exactly like `animation` does — written by `PaperCanvas.tsx` on load/switch, read into `buildCurrentPayload()` for autosave, and otherwise mutated only by the panel's own `renameLayer(id, name)` action (double-click a row to edit, Enter/blur commits, Escape cancels — the same inline-edit pattern `TopBar.tsx` already uses for the project name). A blank commit clears the override, reverting to the inferred name. `computeLayerList()` takes the overrides map as a second argument: a renamed path uses its override name as-is and is excluded entirely from the inferred-kind numbering, so renaming "Rectangle 2" to "Background" leaves the remaining rectangle as plain "Rectangle", not "Rectangle 1" — the numbering always reflects only the *un-renamed* paths of a kind.

Since renaming doesn't touch Paper.js geometry, it needed its own subscription hook (mirroring the existing `animation` one) in `PaperCanvas.tsx`: `if (state.layerNameOverrides !== prevState.layerNameOverrides) { refreshLayers(); scheduleAutosave() }` — `refreshLayers()` because nothing else would rebuild the list to show the new name, `scheduleAutosave()` because nothing else would persist it.

**Both side panels (Layers, Properties) resize horizontally**, mirroring the Timeline's existing vertical resize handle (`Timeline.tsx`'s `handleResizeStart`/pointer-capture pattern, just on `clientX` instead of `clientY`) — local component state, not persisted, same as the Timeline's own height. Clamped to a 160–480px range.

**The resize handle must sit fully inside its own panel's box, not straddle the edge into the sibling.** The first version placed each handle half-overlapping its neighbor (`right: -4px` on the Layers panel, `left: -4px` on Properties) to look flush with the panel edge — this silently broke the Layers panel's handle specifically: `elementFromPoint` at the handle's own coordinates resolved to the `.LayersPanel` element, not the handle, so drags did nothing. Root cause: `overflow-y: auto` (set on both panels, needed for scrolling the row/property list) implicitly sets `overflow-x` to `auto` too per the CSS spec whenever only one axis is set explicitly, so the half of each handle sticking out past its panel's own box was clipped out of the hit-testing region. It happened to still work on the Properties panel by coincidence (its handle's clickable center landed just inside the clip boundary) but not on Layers (whose equivalent center landed just outside it) — fixed by keeping both handles entirely within their own panel (`right: 0`/`left: 0`, no negative offset) rather than relying on that coincidence.

## Fixed: Timeline fields/overlay went stale while scrubbing

Two compounding bugs, both found from a user report ("moving to a timeframe doesn't show updates to transformed objects") and confirmed by reproduction before fixing:

1. The playhead-change handler in `PaperCanvas.tsx` called `applyAnimationAtTime` (which correctly moves/rotates/recolors the live path) but never refreshed the selection overlay or `selectedPathProps` — the data Timeline's property rows and the Properties panel read from. The canvas was right; the panels were stale, only updating on selection changes. Fixed by splitting `redrawOverlay` into `refreshSelectionDisplay` (overlay redraw + `selectedPathProps` refresh, no side effects) and the autosave-scheduling wrapper around it, and calling the former on every playhead change too — without triggering autosave on every animation frame during playback.
2. Separately, `Timeline.tsx`'s per-property `valueOverrides`/`colorOverrides` (used to preview a value before clicking "Key") never got cleared after the keyframe was actually set, so a field stayed pinned to whatever was last typed regardless of scrubbing, masking even the corrected live value from fix (1). Fixed by clearing the relevant override once its keyframe is committed.

Verified precisely: keyed X at 355 (t=0) and 555 (t≈end), confirmed the field showed ~455 at the midpoint scrub and progressed smoothly (405→573) across five samples during actual playback — not just manual scrub clicks.

## Direct manipulation extends animations already in progress

Resolves the "no auto-keying" gap: dragging a shape (or editing its position/fill/stroke via the Properties panel) while in Animate mode now keeps the keyframe system in sync. The design call made here (not explicitly specified, picked as the safest default): **direct manipulation extends an animation already in progress — it never starts a new one.**

- If the property already has a keyframe at exactly the current playhead time, its value is updated (time/easing unchanged).
- If the property is already animated (has a track from being keyed at least once for this path) but has no keyframe at this exact time, a new one is inserted there, inheriting easing from whichever existing keyframe is nearest in time — so posing a new frame doesn't reset the curve to linear.
- If the property has never been keyframed for this path at all, direct manipulation is left exactly as it was: a plain, unrecorded edit, same as Draw mode. Dragging a shape you've never animated doesn't suddenly start animating it.

`withKeyframeAutoInserted()` (`animation.ts`) implements this; `syncKeyframesAfterDirectEdit()` (`canvasEngine/animationPlayback.ts`) is the shared hook — called from the Select tool's drag-commit and resize/rotate-handle commit (`tools.ts`) and from `PaperCanvas.tsx`'s `applyPropsEdit` (position/stroke/fill edits). It checks x/y, width/height, and both color trios directly from the live path's bounds/colors; rotation is different (see next section) and is passed in explicitly as a delta by the caller.

Verified all three cases: dragging at an already-keyed time updates that keyframe (1→1, value changes); dragging at a new time on an already-animated property inserts a new keyframe (1→2) whose value survives a scrub-away-and-back; dragging a property that's never been animated creates nothing (0→0), confirmed as a control alongside the other two in the same test run.

## Resize/rotate handles, easing editing, and a sticky-header regression

Three follow-up improvements to the animation-authoring experience, done together:

**1. Resize and rotate handles on the Select tool's selection overlay.** Previously width/height/rotation/scale could only be set by typing into the Timeline's own fields — there was no on-canvas handle, which was the reason `syncKeyframesAfterDirectEdit` didn't cover those properties (see the old "Known gaps" entry this resolves). `overlay.ts`'s `drawTransformHandles()` draws 8 resize handles (corners + edge midpoints) and one rotate handle (offset above top-center, screen-space-constant size regardless of zoom) whenever the Select tool has a single path selected; `tools.ts`'s `createSelectTool` checks these via `hitTestOverlay` before falling through to its normal path-hit/marquee logic.

- Resize drags the dragged corner/edge while the opposite corner/edge stays anchored (`computeResizedBounds`, pure and unit-tested), by directly reassigning `path.bounds` — the same mechanism `applyGeometryAtTime` already uses for width/height keyframes, so it composes with existing behavior for free. Shift preserves aspect ratio on a corner drag. Resize syncs through the generic x/y/width/height path in `syncKeyframesAfterDirectEdit` — no new sync code needed.
- Rotate calls `path.rotate()` directly on the live path (shift snaps to 15° increments) and tracks the gesture's net rotation in degrees. Because rotation keyframes store an absolute angle relative to captured rest geometry (not something live Paper.js state can be read back as — see the rest-geometry architecture note above), the handle can't reuse the generic bounds-reading sync path: it passes the gesture's rotation *delta* to `syncKeyframesAfterDirectEdit`, which — only if a rotation track already exists for the path (auto-key never starts a new animation, same rule as everything else) — adds that delta to whatever the rotation track currently evaluates to at the playhead and auto-keys the result.
- Deliberately *not* synced: resizing never touches `scale` keyframes. `scale` is a rest-geometry-relative multiplier (a parallel, older mechanism for proportional animation); resize's width/height-based bounds mutation is a different, newer mechanism, and `applyGeometryAtTime` already lets width/height tracks override scale/rotation's rest-based sizing when both exist. Driving `scale` from a resize-handle delta would make two mechanisms fight over the same pixels.

**2. Click a keyframe diamond to edit its easing**, instead of delete-and-re-add being the only way to change it. A plain click (no horizontal movement past a small threshold) opens an inline editor in the Timeline header with an easing `<select>` (writes through the existing `setKeyframe` with the keyframe's own time/value, easing only) and a Delete button; works for both plain-property and color-trio (all three channels share one editor) rows.

   Implementing this exposed a real interaction conflict: a `dblclick` (the existing delete gesture) is two independent `mousedown`→`mouseup` pairs, and the first pair alone looks exactly like a single click — opening the easing editor **immediately** on every click meant the editor popped in between a dblclick's two clicks, which (since the editor is in-flow, not floating) shifted the Timeline's layout and made the dblclick's second click land somewhere else, silently breaking delete. Fixed by delaying the editor open by `DBLCLICK_WINDOW_MS` (300ms) and having the dblclick handler cancel the pending timer first — standard click/dblclick disambiguation, applied here because the popover affects layout instead of being a floating overlay.

**3. Timeline header controls (`.Timeline-controls`) are now `position: sticky`** inside the scrollable panel body, so play/duration/easing/Done stay visible while property rows scroll underneath — a user-requested tweak, done alongside the above.

**Regression caught by the new e2e tests before merge, not after**: making the header sticky (`z-index: 2`) silently broke the Timeline's own resize handle (`.Timeline-resizeHandle`, `z-index: 1`, positioned to straddle the panel's top edge) — the sticky header now painted over it, so dragging the handle hit the header instead and did nothing. Caught because a new e2e test needed to shrink the Timeline (to stop it from overlapping the canvas — see the Testing section above) and the shrink silently no-opped. Fixed by raising the handle's z-index above the header's. This is also why the pre-existing "direct manipulation updates an existing keyframe" test got reworked: it turned out to have the same latent gap — its drag coordinates also landed on the Timeline panel instead of the canvas, and the test never asserted the value actually *changed*, only that it stayed consistent across a scrub — so it was silently passing without exercising the drag at all. Both are fixed now (the fixed test asserts `afterDrag !== beforeDrag`).

## Node anchors visible from the Select tool, and a live resize/rotate readout

Two more follow-ups, requested after trying the resize/rotate handles above.

**Nodes no longer require switching to the Node tool first.** `drawNodeOverlay()` gained a `showHandles` param (default `true`); the Select tool now also calls it with `showHandles: false` whenever it has a single selection, drawing anchor dots (no in/out handle-line clutter) alongside the resize/rotate handles. Clicking and dragging one of those anchors moves that node directly from Select — `createSelectTool` handles the whole gesture itself (mutating `segment.point` inline, exactly like the Node tool would) rather than handing off mid-drag, because **Paper's active tool can't be switched mid-gesture**: `PaperCanvas.tsx`'s tool-activation subscription only calls `.activate()` on a `Tool` when the store's `tool` field changes, and switching it immediately on `mousedown` would reroute the rest of the gesture's `drag`/`up` events to the Node tool's handlers — which never got a `mousedown` of their own, so their internal drag state (`dragPath`/`drag`) would still be `null` and silently do nothing. The fix: keep handling the drag in `createSelectTool` throughout, and only call `setTool('node')` in its own `mouseUp`, once the gesture is fully done — so the toolbar, Properties panel, and the node's handle lines all switch into Node mode a beat after release, not mid-drag.

**Live on-canvas label during a resize/rotate drag.** Neither gesture had any readout of the value while dragging — surfaced directly as "I can rotate object but cannot see the rotation value." `overlay.ts`'s `drawTransformLabel()` draws a small pill near the cursor (e.g. `49°` while rotating, `120 × 80` while resizing), redrawn every drag frame from `tools.ts` right after `redrawOverlay()` clears and rebuilds the rest of the overlay — it doesn't need its own state since it's just redrawn fresh each frame rather than persisted. Deliberately transient: it only exists during the drag itself, not after release, because there's nowhere to put a persistent readout — Paper.js has no concept of a path's "current rotation" outside of keyframe data (see the rest-geometry note above), so a static non-animated shape has no rotation value to display once you let go.

## Timeline grouped by shape

The follow-up explicitly deferred when the Layers panel shipped: the Timeline previously only ever showed property rows for whichever single path was currently selected, with no way to see or compare another shape's keyframes without reselecting it first.

**The Timeline now renders one collapsible group per layer**, reusing the same `layers` list (and therefore the same frontmost-first ordering and inferred/custom names) the Layers panel already computes — `Timeline.tsx` maps over `layers` instead of branching on a single `selectedPathId`. Each group is a header button (shape name + a dot if it has any keyframes) plus, only for the currently *selected* shape, the full interactive body — the existing `PROPERTY_DEFS`/`COLOR_ROW_DEFS` rows, Key buttons, draggable keyframes, and easing editor, unchanged from before this feature. Other groups collapse to just their header.

**Only one group is ever fully interactive at a time, by design.** Editing a property (dragging a keyframe, typing a value, clicking Key) needs `selectedPathProps` — a live readout of the path's current Paper.js state that only exists for the single currently-selected path (see the architectural rule in CLAUDE.md: only `PaperCanvas.tsx` reads live Paper.js state, and it only computes this for the selection). Rather than build a second, read-only rendering path for non-selected shapes' rows, clicking any group's header simply selects that shape (`setSelection([layer.id])`) — the same action the Layers panel and canvas clicks already use — which both expands that group and gives it live, editable values. This keeps the Timeline's row-rendering logic exactly as it was; the only new code is the grouping wrapper and the header's `hasKeyframes()` check (`animation.tracks.find(t => t.pathId === id)?.properties.some(p => p.keyframes.length > 0)`) that drives the collapsed-state dot.

Verified with two shapes: keying a property on one shows its dot while collapsed, clicking the other shape's header switches which group is expanded *and* updates canvas/Properties-panel selection, and the first shape's dot persists correctly while its group is collapsed.

## Fixed: side-panel resize could desync the ruler

Reported directly: "horizontal ruler looks a bit broken" shortly after the Layers/Properties panel resize feature shipped. Root cause: a resize drag updated the panel's width React state — and therefore `CanvasWrap`'s flex layout, which `PaperCanvas.tsx`'s `ResizeObserver` reacts to by re-fitting the view and pushing a fresh `viewTransform` that `Rulers.tsx` redraws from — on *every* raw `pointermove` event. A fast continuous drag fires far more of those than the browser can deliver `ResizeObserver` notifications for in a frame (visible in the browser console as "ResizeObserver loop completed with undelivered notifications"), and the Rulers canvas could end up drawn against a layout that was already stale.

Fixed by throttling the width update to once per animation frame — `usePanelResize.ts` (a small shared hook now used by both `LayersPanel.tsx` and `PropsPanel.tsx`, replacing the duplicated drag-handling each previously had inline) tracks the latest computed width in a ref on every `pointermove`, but only calls `setWidth` from inside a single pending `requestAnimationFrame` callback, matching the browser's own update cadence instead of outrunning it.

This bug was hard to pin down with an automated test: a synthetic Playwright drag plus an assertion with *no* settling delay fails identically whether the throttle is present or not (both show a harmless one-frame lag — inherent to any React state → effect → `ResizeObserver` → redraw chain, fix or no fix), while any settling delay at all (even ~16ms, one frame) was enough for the *unfixed* version to self-correct too in this harness's timing. The committed test (`e2e/layers.spec.ts`) therefore only pins down the steady-state result after a drag, not the exact race — real confidence that the fix works came from manually reproducing the original bug via a fast multi-step drag + immediate screenshot (reliably broken before the fix, reliably fine after) rather than from the automated suite alone.

## "No stroke", matching the existing "no fill"

Fill already supported `null` (a "No fill" checkbox existed in `PropsPanel.tsx`); stroke didn't have the equivalent, so a path could always only have *some* stroke color, never none. Extended the same pattern stroke never had: `PropsEdit`'s `stroke` kind now takes `color?: string | null` (was `string`) and `SelectedPathProps.strokeColor` is now `string | null` (was `string`) — `PaperCanvas.tsx`'s `applyPropsEdit` sets `path.strokeColor = null` the same way it already did for fill, and `overlay.ts`'s `computeSelectedPathProps` reads it back as `null` instead of defaulting to `'#000000'` when `path.strokeColor` is unset. `PropsPanel.tsx` gained a matching "No stroke" checkbox, and the stroke color swatch and Weight field both disable when it's checked (Figma does the same — a weight on no stroke has nothing to apply to).

No animation-system changes were needed: `strokeColorR/G/B` keyframes are a separate, pre-existing mechanism (same as `fillColorR/G/B`) that only runs when all three channels evaluate non-null, and playback already guarded every stroke-color read with `if (path.strokeColor)` — this was exactly the same shape as the fill case, just extended to the one spot (`PropsPanel.tsx`'s Stroke section) that hadn't caught up to it yet.

Caught one thing worth noting while testing by hand, not a bug: the sample star shape (`sampleShapes.ts`) has no `stroke` attribute in its SVG at all, so it imports with `strokeColor: null` already — "No stroke" showed checked immediately on import, which is correct (SVG's default stroke is `none`), not a sign the feature was misfiring. Verified properly using a freshly-drawn rectangle (born with both a fill and a stroke) instead.

## Fixed: stale rest-geometry snapshot outliving its last rotation/scale keyframe

The known gap called out when the rest-geometry mechanism first shipped: `PathTrack.restSegments`/`restCenter` (captured once, the first time rotation or scale is keyframed for a path) used to only get cleared when the *entire* path track was pruned (i.e. every property on that path had zero keyframes). If an unrelated property — say, X — was also keyframed on the same path, deleting all of that path's rotation/scale keyframes left the rest snapshot sitting there with nothing left that needed it. The next playhead change would still run `applyGeometryAtTime`'s `if (pathTrack.restSegments && pathTrack.restCenter)` reset-to-rest step (in `canvasEngine/animationPlayback.ts`), silently overwriting any node-edit made to the path in the meantime.

Fixed in `withKeyframeRemoved` (`animation.ts`): after pruning the removed keyframe's property track, it now also checks whether `rotation` or `scale` still have any keyframes left on that path *independent of whether the whole path track survives* — if neither does, `restSegments`/`restCenter` are deleted from the track right there, not just when the track itself empties out.

One related, intentional side effect worth noting: deleting a path's last rotation/scale keyframe no longer resets the path to its pristine rest shape on the next evaluation — since there's no rest snapshot left to reset to, the path simply stays at whatever its live geometry currently is. This is arguably more correct than the old behavior (an implicit, easy-to-miss "snap back to original" the moment the last keyframe was deleted) and is consistent with how an un-keyframed property has always behaved elsewhere in this codebase: once nothing is tracking it, Paper.js's current segment data is simply the truth, full stop.

Caught the real bug (not just in theory) with a unit test harness before writing the fix: reproduced it by keying both X and rotation on the same path, deleting only rotation's keyframe, and confirming `hasRestGeometry` still returned `true` against the pre-fix code — then verified the same scenario end-to-end (key X, key rotation at identity, delete the rotation keyframe, node-edit the path, scrub the playhead away and back) failed identically against the pre-fix code (the node-edit reverted) and passed after the fix, in both `src/animation.test.ts` and `e2e/animation.spec.ts`.

## Cursor affordances for the Select/Node tool handles

Reported directly, with a screenshot showing the resize/rotate/node-anchor overlay: the canvas cursor was always the plain default arrow, regardless of what hovering would actually do — no visual hint that a corner was resizable, an edge was draggable, the handle above the shape would rotate it, or the shape itself was movable.

`overlay.ts`'s new `cursorForOverlayHit(hit)` maps each `OverlayHit` variant to a CSS cursor: resize corners/edges to the matching directional cursor (`nwse-resize`/`nesw-resize`/`ns-resize`/`ew-resize`, by corner), node anchors/bezier handles to `pointer`, and rotate to a custom cursor — CSS has no built-in "rotate" keyword, so this is a small inline SVG data URI (a circular arrow, white halo behind a black stroke so it stays visible on any canvas background, light or dark) with a `grab` fallback. `tools.ts`'s Select and Node tools call it from a new `onMouseMove` handler (hover) and set the matching cursor explicitly at the start of a resize/rotate/anchor/shape drag in `onMouseDown` — `onMouseMove` doesn't fire while a button is held (Paper.js routes those events to `onMouseDrag` instead), so the drag-time cursor has to be set once up front rather than recomputed continuously. `PaperCanvas.tsx` also resets the cursor on every tool switch, so a handle-specific cursor from the previous tool can't stick around on the new one until the next mousemove.

Scoped to the Select/Node tool interactions shown in the report — the drawing tools (Pen, Rectangle, Ellipse, Ruler, Add Point) still just show the default cursor. A `crosshair`-style cursor for those would be a reasonable, cheap follow-up if wanted, but wasn't part of what was reported.

## Fixed: GIF export ignored the "Loop timeline playback" setting

The exported GIF's loop behavior never matched the in-app Timeline's own "Loop timeline playback" setting — it always looped forever (`gif.js`'s own default `repeat: 0`), regardless of whether that setting was on or off. `exportGif()` (`canvasEngine/svgExport.ts`) now passes `repeat: storeRef.current.settings.loopPlayback ? 0 : -1` explicitly, matching `createPlaybackController`'s own stop-vs-loop behavior in `animationPlayback.ts`.

Video (`.webm`) export has no equivalent fix: there's no embeddable "loop" flag in the WebM/Matroska container format — looping is purely a player-side behavior (a `<video loop>` attribute, a media player's own repeat setting), nothing a recorded file can carry. Nothing to do here; not a gap, a hard format limitation.

**New test coverage caught a real bug in the test itself, not the fix**: `gif.js`'s worker only writes the optional `NETSCAPE2.0` looping extension block when `repeat >= 0` (`node_modules/gif.js/dist/gif.worker.js`), omitting it entirely for `-1` — so its presence/absence in the downloaded bytes is a reliable, simple signal to assert on. The first version of the new e2e test assumed "Loop timeline playback" defaults to *on* and got the pass/fail assertions backwards; `editorStore.ts`'s actual default is `loopPlayback: false`. Both tests now set the setting explicitly rather than relying on an assumed default.

Also added, since they were previously untested entirely: a WebM export test (asserts the downloaded file's first 4 bytes match the EBML/Matroska magic signature `1A 45 DF A3`) and a strengthened PNG test (previously only checked that a file path existed, not that it contained real PNG data — now asserts the 8-byte PNG signature and a non-trivial file size).
